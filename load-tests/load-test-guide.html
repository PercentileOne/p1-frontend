Concurrent session load test

A JMeter test plan for Azure Load Testing, targeting the three endpoints flagged as the real risk surface in the infrastructure reference — set up once, then run it a few times over the next week or two as changes land.

What's in this folder

Everything needed to create and run the test in Azure Load Testing.

interview-load-test.jmxThe JMeter test plan — 3 thread groups, one per endpoint, independently scalable.
azure-load-test-config.yamlAzure Load Testing config referencing the plan above — engine count, failure criteria, default parameters.
sample-answer.wavSmall synthetic audio clip (4s tone) — the payload for the transcription thread group.
README.mdQuick command reference.

What it tests

One thread group per endpoint — run all three together, or disable the ones you don't need for a given pass.

Thread groupEndpointWhat it's really checking
1/api/ai-proxyWhether the single-instance App Service and the Model Router hold up under concurrent AI calls. Default body is a cheap 1-line probe — see the cost note below.
2/api/ai/transcribeWhisper transcription, called directly against OpenAI with no Model Router failover — its own separate quota ceiling.
3/api/interviews/uploadMetadata + recording upload. Requires a real bearer token — see setup step 3.

Setup

  1. Create the Azure Load Testing resource (one-time)
    If you don't already have one in p1-core:
    az load create --name p1-load-testing --resource-group p1-core --location uksouth
  2. Create the test
    az load test create \
  --name interview-load-test \
  --resource-group p1-core \
  --load-test-config-file load-tests/azure-load-test-config.yaml \
  --test-plan load-tests/interview-load-test.jmx
  3. Upload the audio sample and (optionally) a bearer token
    In the Azure Portal → your Load Testing resource → the test → Test files, upload sample-answer.wav so thread group 2 can find it. For thread group 3, grab a real token from a logged-in candidate session (browser dev tools → Application → local storage, or the network tab on any authenticated request) and pass it at run time — it's short-lived, so fetch a fresh one before each run rather than committing one anywhere.
  4. Run it
    az load test-run create \
  --test-id interview-load-test \
  --resource-group p1-core \
  --env authToken=<paste a fresh token>

Before you push past 20 users

Cost — read this before a big run

The default /api/ai-proxy body is a deliberately cheap one-line probe, not a real interview generation call — running 150 of those costs pennies. The commented-out block inside the HTTP Request (in the .jmx, or just search for "production-shaped body") is the real thing: a full session-generation prompt matching what sessionPrepareClient actually sends. Swapping to that and running it at 150–200 concurrent users is a genuinely production-cost run — do it once, deliberately, not on every iteration.

Ramp up, don't jump straight to 150

Step through a few stops first — cheaper to find where things bend at 50 than to discover it at 150 with no data on where the curve actually turns.

Reading the results

The Aggregate Report (in the .jmx, and mirrored in the Azure Portal's own test-run dashboard) breaks results down per thread group. Averages hide the failure mode this test exists to catch — a single App Service instance that's fine most of the time and then chokes under the tail — so look at p90/p99, not just the average.

SignalLikely means
Error % climbs on thread group 1 specificallyThe single-instance App Service (no autoscale) or the Model Router's own quota — check App Insights' requests table for which.
Thread group 2 slows or errors while 1 stays healthyWhisper/OpenAI's own rate limit — this one has no Model Router failover to fall back on.
Thread group 3 all return 401Expected if no (or an expired) bearer token was passed — not an infrastructure finding.
p99 response time spikes but error % stays lowThings are queuing, not failing outright — often the earliest sign of the single-instance ceiling before it starts actually rejecting requests.
