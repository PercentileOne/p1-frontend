Building a World-Class Digital Product · Chapter Note — Reliability at Scale

Never depend on one AI model

A beginner's walkthrough of Azure AI Foundry's Model Router — one Azure endpoint that automatically spreads your app's AI calls across 20+ models from OpenAI, Anthropic, Meta, DeepSeek and xAI, with built-in failover, using nothing but the Azure CLI.

⏱ ~25 minutes 💻 Terminal + an Azure account 💰 Pay-as-you-go, no upfront commitment

If you've only ever called one AI provider directly — a single OpenAI or Anthropic API key baked into your backend — this chapter changes that. You'll stand up an Azure resource that speaks to your app exactly like OpenAI does, except behind the scenes it can hand each request to whichever underlying model suits it best, and automatically try another one if the first choice is unavailable. Your product stops depending on any single company having a good day.

📖
Concept — Model Router

A trained routing model, not a proxy or a script. You send it a normal chat-completion request; it reads the prompt and decides, per request, which underlying model — a fast cheap one or a slow capable one — actually answers it. You never choose the model yourself.

What you'll need

  • An Azure account with an active subscription (a free trial works to follow along)
  • Azure CLI installed — version 2.60 or later (az --version to check, az upgrade to update)
  • Ten minutes of patience for Azure resource provisioning, which is never instant

The seven steps

Everything below is real — run in that exact order, this is what actually stands the whole thing up.

1

Sign in and pick your subscription

If you've used the Azure CLI before, you may have several subscriptions attached to your account. Confirm which one you're working in before creating anything.

terminal
az login
az account set --subscription "your-subscription-id"
2

Register the Cognitive Services provider

Every Azure subscription starts with most "resource providers" switched off, to keep the default surface area small. AI Foundry resources live under Microsoft.CognitiveServices — if this is the first AI resource in the subscription, you'll need to switch it on once. It's free and it's permanent; you'll never run this again for future projects in the same subscription.

terminal
az provider register --namespace Microsoft.CognitiveServices --wait
⚠️
Gotcha

Skip this and your very first resource-creation command fails with MissingSubscriptionRegistration. It's not a permissions problem and it's not your syntax — it just means this specific subscription has never used this specific Azure service before. Run the line above and retry.

3

Create the AI Foundry resource

This is the actual Azure resource your app will talk to. Give it a name that's globally unique (it becomes part of a URL), and pick a region close to where your app itself is hosted — the resource and your server exchanging data across continents adds real latency to every single AI call.

terminal
accountName="myapp-model-router"
resourceGroup="myapp-rg"
location="westeurope"

az cognitiveservices account create \
  -n $accountName -g $resourceGroup \
  --custom-domain $accountName \
  --location $location \
  --kind AIServices --sku S0

The --custom-domain flag matters more than it looks — it's what turns your generic Azure resource into its own addressable endpoint, https://myapp-model-router.openai.azure.com, which is the URL your app will actually call.

4

Confirm Model Router is available to you

Not every model is available in every region or on every subscription tier. Before deploying, check what your new resource can actually see — this also teaches you the exact model name and version string Azure expects, which you'll need in the next step.

terminal
az cognitiveservices account list-models -n $accountName -g $resourceGroup \
  | grep -A3 '"model-router"'

Look for a version number like 2025-11-18 — Azure dates its Model Router releases rather than numbering them, and this specific version stays actively maintained (new underlying models get added to it automatically) rather than being frozen the way older dated versions are.

5

Deploy it

"Deploying" here doesn't mean shipping code — it means telling Azure to actually provision capacity for this specific model against your resource, under a name you choose. That name is what your app puts in the model field of every request; it never needs to know which real model answered.

terminal
az cognitiveservices account deployment create \
  -n $accountName -g $resourceGroup \
  --deployment-name model-router \
  --model-name model-router \
  --model-version "2025-11-18" \
  --model-format OpenAI \
  --sku-name GlobalStandard \
  --sku-capacity 1

This typically finishes in under a minute. Confirm it actually succeeded before moving on — a silent partial failure here is the most common reason step 7 doesn't work:

terminal
az cognitiveservices account deployment show \
  --deployment-name model-router -n $accountName -g $resourceGroup \
  --query "properties.provisioningState"
# → "Succeeded"
6

Grab your endpoint and key

terminal
az cognitiveservices account show -n $accountName -g $resourceGroup \
  --query "properties.endpoint" -o tsv

az cognitiveservices account keys list -n $accountName -g $resourceGroup \
  --query "key1" -o tsv
⚠️
Gotcha

The properties.endpoint field returns a .cognitiveservices.azure.com domain, which looks right but isn't the one you want for chat completions — that domain fronts dozens of unrelated Azure AI services (Speech, Translator, Vision...). The one your app actually calls is the .openai.azure.com domain, built from the same resource name: https://<your-account-name>.openai.azure.com.

7

Make your first call

This is the entire integration. Notice the request body is the same OpenAI-style chat-completions shape you'd send to OpenAI directly — the only two things that change from a direct OpenAI integration are the URL and the auth header.

terminal
curl -X POST "https://myapp-model-router.openai.azure.com/openai/v1/chat/completions" \
  -H "api-key: YOUR_KEY_HERE" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "model-router",
    "messages": [
      { "role": "user", "content": "Say hello in one sentence." }
    ]
  }'

The JSON that comes back includes a model field naming whichever real model actually answered — that's how you can watch, request by request, which model the router is reaching for.

What you get for free

None of the following needed any extra code — it's what the router does by simply existing between your app and the model providers.

Automatic failover
If the model the router would normally pick is having an outage or a rate-limit spike, it transparently tries the next-best model instead. Your app never sees the failure.
Cost-aware routing
Simple requests get routed to small, cheap, fast models. Requests that genuinely need deeper reasoning get routed to a more capable (and more expensive) model — automatically, per request, based on what you send it.
Natural output variety
Because different requests can land on different underlying models, two calls with an identical prompt won't necessarily come back phrased identically — useful any time you don't want your output to feel templated or become guessable.
One bill, one key
You're not managing separate API keys, separate billing relationships, or separate rate limits for OpenAI, Anthropic, and everyone else. It's all one Azure resource.
💡
Tip — before you trust it in production

Model Router defaults to "Balanced" mode, which weighs quality and cost together — for latency-sensitive, real-time features, that can mean it reaches for a slower, more capable model than the task strictly needs. Test your actual prompts against it and measure real response times before assuming it's a drop-in replacement for a single fast model you were calling directly. If it's consistently too slow, "Cost" mode (set via a Custom deployment in the Foundry portal, not currently exposed through the CLI flags shown here) biases harder toward speed and price.

Wiring it into an existing app

If your backend already calls OpenAI directly, the change is almost always this small: a new base URL, a header rename (Authorization: Bearer <key> becomes api-key: <key>), and setting model to your deployment name instead of a specific model like gpt-4o-mini. If your AI calls already flow through a single proxy endpoint on your own backend — which they should, for the reasons in the next chapter — you change it in exactly one place, and every feature that calls that proxy inherits the upgrade without knowing anything changed.
