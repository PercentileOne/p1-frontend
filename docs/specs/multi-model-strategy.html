Should the interview engine depend on one AI model?

Your question after tonight's demo: is a single model too fragile to build hundreds of thousands of interviews on — and if we spread across two to four, how do the big platforms actually do it, and what does Microsoft give us for free?

⚠️
What actually broke tonight

Not model reliability. The safety net that tops up a short question count was re-running the entire generation — 10 questions, 2 MCQs, 3 intros — up to twice more, and each retry cost another 10–20s. That routinely ate the 55-second window Sarah and James have to arrive personalised, so they fell back to generic lines. Fixed by cutting the retries and going straight to a small, targeted top-up call. Already deployed.

✓
Worth separating

Multi-model redundancy wouldn't have prevented tonight's bug — the model answered correctly every time, we just called it more than necessary. It's still the right question to ask for the platform's next stage, for different reasons below.

01 What's actually available

Three shapes this can take, in order of how much you build yourself:

Call providers directly, write your own routing Most work

OpenAI, Anthropic, Google direct API calls from Explain.Api, with your own retry/fallback code choosing between them. Full control, but you own every failure mode, rate limit, and pricing quirk for each provider separately.

An LLM gateway in front of everything Moderate

A proxy layer (Bifrost, Portkey, LiteLLM and similar) sits between your app and every provider, speaking one API shape outward and handling failover, retries, and cost tracking centrally. Popular where teams are already multi-cloud or want provider choice beyond what Azure's catalog carries.

Azure's own multi-model router Least work

One Azure AI Foundry deployment exposes 18 models from five providers behind a single endpoint, with automatic failover and cost-aware routing built in — no gateway to run yourself. Detailed below, since P1 is already fully committed to Azure.

02 How the large platforms do it

The pattern converges the same way almost everywhere it's been written up, and it's shifted meaning over the past couple of years — multi-model started as a cost-optimisation tactic and is now treated as resilience engineering in its own right.

  • Fallback chains. A primary model handles the request; on timeout, error, or a rate limit, the same request replays against a secondary model automatically, invisibly to the user.
  • Complexity-based routing. Cheap, fast models absorb simple requests; expensive, capable models are reserved for the ones that actually need them. This is as much a cost lever as a reliability one.
  • Provider diversification as insurance. Depending on one vendor means one vendor's bad day — an outage, a sudden rate-limit change, a quiet quality regression after a model update — becomes your bad day too, with no lever to pull.
  • A gateway as the seam. Almost nobody hand-rolls this per call site. One control point owns retries, circuit-breaking, health checks, and observability, so the application code stays simple and provider-agnostic.

03 What Microsoft actually offers

Two distinct things carry the "Azure OpenAI" name, worth telling apart:

Azure OpenAI Service — same models, Azure-hosted

This is what Explain.Api already points at conceptually (currently via a direct OpenAI key rather than the Azure-hosted version). It's still fundamentally one provider's models — resilience here means deploying the same model across multiple Azure regions and load-balancing or failing over between them via API Management, plus optional provisioned throughput (PTU) for guaranteed capacity instead of shared quota. Solves "Azure has an outage in one region" — doesn't solve "OpenAI's models are having a bad day."

Azure AI Foundry — the broader model catalog

The newer, bigger thing: a catalog of over 10,000 models curated from OpenAI, Anthropic, Meta, Mistral, DeepSeek, xAI, Cohere, Hugging Face and others, all reachable through Azure with a single billing relationship and set of enterprise controls.

Model Router — the specific piece that answers your question

This is the part worth focusing on. Model Router is a single Foundry deployment that puts 18 models from OpenAI, Anthropic, DeepSeek, Meta, and xAI behind one endpoint, and picks the right one per request in real time based on complexity, cost, or a quality target you set. Critically for tonight's conversation: automatic failover to another model is a built-in behaviour when a provider is unavailable — not something you write.

Recommendation

Model Router is the natural fit — it's already inside the Azure account P1 is committed to, and it happens to solve both things you asked for at once. Automatic cross-provider failover answers the reliability concern directly. And because different requests can land on different underlying models, no two sessions phrase questions identically even at the same settings — a real, structural answer to "we don't want people memorising and sharing answers," not just a temperature tweak.

The migration is small in shape: Explain.Api's ai-proxy already just forwards a chat-completions-style request to api.openai.com. Pointing it at a Foundry Model Router deployment instead is largely a URL and auth change, not a rewrite — though it's worth testing carefully against this app's specific prompts (the heavy sessionPrepareClient call in particular) before trusting it in production, since different underlying models may follow the JSON schema and word-count instructions slightly differently from GPT-4o-mini today.

This is a proposal, not a plan already in motion — happy to scope the actual migration whenever you want to move on it.
