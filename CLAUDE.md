## 0. The one rule that matters most

**No third-party API key (OpenAI, ElevenLabs, Anthropic, etc.) is ever shipped to the browser — not as a primary path, not as a "resilience fallback."** Every call to an external AI/API provider goes through the `.NET` backend (`src/backend/Explain.Api`), which holds the key server-side and proxies the request. A key baked into a Vite build is visible to anyone via view-source or devtools, full stop — this has already happened once (see incident below) and cost real money.

**Incident, 2026-08-17:** `src/frontend`'s `LearnPanel.tsx` and `ProfileVideoPage.tsx` called OpenAI directly from the browser using `VITE_OPENAI_API_KEY`, exposed in the public JS bundle. Separately, most of the app's `/api/ai-proxy` calls used a **relative path** (`fetch('/api/ai-proxy')`), which silently 404'd because this specific Static Web App has its own integrated Functions runtime with no `ai-proxy` function of its own — so the client-key fallback was doing more work than anyone realized. Fixed by routing every AI call through an absolute URL (`${VITE_EXPLAIN_API_URL}/api/ai-proxy`) and deleting the client-key path entirely. **If any AI feature in this app misbehaves or silently degrades, check for a relative `/api/*` path first** — that's the recurring failure mode.

**A second, separate incident found the same day:** a prior agent session had created its own generically-named OpenAI API key and used it directly for its own agentic work (calling models like `gpt-5.6-sol`, `gpt-5.3-codex` that this codebase never references — every AI call here hardcodes `gpt-4o-mini`), racking up $84.61 in charges on Francis's personal account over about three weeks. **No Claude Code session should ever create or use its own third-party API key (OpenAI, Anthropic, etc.) for its own work billed to the user.** A project's API key exists only for that project's own server-side backend code to call, never for an agent to use directly for anything else.

## 2. Mandatory tech stack — no substitutions

- **Backend:** .NET 10 Minimal APIs only. ASP.NET Core, EF Core, Azure Functions as C# isolated worker. **Never** Node.js/Express for API, auth, or business logic. Vertical-slice architecture, CQRS-style handlers, MediatR where the codebase already uses it.
  - The one sanctioned exception: `src/frontend/api/share-meta` is a small Node.js Azure Function that patches Open Graph meta tags into the static HTML shell for social-share crawlers, because Azure Static Web Apps route rewrites can't proxy to an external `.NET` domain. This was an explicit, one-off, user-approved exception — not a precedent. Don't add more Node functions without asking first.
- **Frontend:** React 19 + TypeScript + Vite 8 (rolldown bundler) + Tailwind CSS v4 (`@import "tailwindcss"`) + Framer Motion v12 + lucide-react + React Router v7.
  - **Always** use `import type { ... }` for type-only imports. Vite 8's rolldown bundler throws `[MISSING_EXPORT]` on a blank screen if a type is imported with a regular `import { }`.
  - Before adding any `lucide-react` icon import, grep the file first — rolldown throws a hard `[PARSE_ERROR]` on a duplicate identifier if it's already imported.
  - No global state library. Component-local `useState` + module-level in-memory stores.
- **Data:**
  - **Azure SQL** (via EF Core) — users, accounts, subscriptions, billing, permissions, audit logs. Relational, transactional.
  - **Azure Cosmos DB** — profiles, interviews, lessons, alerts, real-time/document-shaped data.
  - **Azure Blob Storage** — audio/video uploads, always via private container + per-request SAS URL, never public access.
  - **Data Lake Gen2** — analytics, AI training data (later phase).

## 3. Known gotchas — check these first

- **JWT auth 401s despite a valid token:** ASP.NET's JWT bearer handler remaps short claim names (`sub`, `email`, `role`) to legacy XML-namespace URIs by default, so `ctx.User.FindFirst("sub")` silently returns `null`. Fix is `opt.MapInboundClaims = false;` in the `.AddJwtBearer(...)` config in `Program.cs` — check this is still set if a new auth-protected endpoint mysteriously can't read claims.
- **Cosmos documents keyed by `id = someOtherField` (userId, candidateId, etc.):** C# property initializers like `public string Id { get; set; } = Guid.NewGuid().ToString();` re-evaluate on every `new` call — they don't share state. Every construction path (including "create if missing" fallbacks) must explicitly set `Id = userId` or the document becomes permanently unreadable by anything that fetches by that id. This exact bug orphaned every user's profile from registration onward until fixed 2026-08-17.
- **`src/frontend/.git`:** this folder has its own leftover nested git repo, pointing at the same remote as the outer `P1` repo but with a diverged history. Running git commands from inside `src/frontend` shows alarming, wrong diffs. Always run git from the outer `P1` root.
- **Relative `/api/*` paths in `src/frontend`:** this SWA has its own integrated Azure Functions (`get-lesson`, `save-lesson`, `share-meta`, etc.) living at `src/frontend/api/`. A relative fetch to a route that only exists on the `.NET` backend (like `/api/ai-proxy`) silently 404s against the SWA's own Functions runtime instead. Any call meant for the real backend must use an absolute URL: `` `${import.meta.env.VITE_EXPLAIN_API_URL}/api/...` ``.
- **Browser-side "Failed to fetch" on an API call can mean the server 500'd mid-request, not that it's unreachable:** if an unhandled exception is thrown after CORS preflight succeeds but during the actual request, the resulting 500 often carries no `Access-Control-Allow-Origin` header — the browser then refuses to expose the response to JS at all, and `fetch()` throws the generic "Failed to fetch" instead of surfacing a readable status/body. This looks exactly like a DNS/network/cold-start problem (and preflight `OPTIONS` checks will still pass, reinforcing that impression) but isn't. **First move: check Application Insights `exceptions` for the endpoint, don't assume network/infra.** Root-caused this way once already, 2026-09-16: the brute-force-lockout commit (`5e09fab`) put `DateTime.UtcNow - lockoutWindow` inline inside an EF Core `.Where()`, which EF can't translate to SQL — it threw on 100% of login attempts, for every account, for ~13 hours before anyone tried logging in. Fixed by precomputing the cutoff `DateTime` outside the query. General lesson: EF Core LINQ `Where()` clauses should use precomputed local variables, not inline arithmetic on `DateTime.UtcNow` or similar — translation failures here are silent until a request actually exercises that path, and manifest as network-looking errors, not query errors.
- **Adding a new page to `src/viewme/public/` doesn't deploy it by default — check `deploy-product-interviewme.yml` first.** That workflow doesn't copy the directory; it hand-copies an explicit, maintained list of `cp` lines into the deploy output. A new `.html` file left off that list silently returns HTTP 200 with the WRONG page's content (`staticwebapp.config.json`'s `navigationFallback` rewrites any unrecognized path to `/index.html`, i.e. `home.html`) instead of a 404 — a status-code check alone says "it works," but the browser shows the homepage at whatever URL you meant to build. Confirmed live 2026-09-16: `gift-interview.html`/`gift-interview-success.html` both returned 200 for over an hour while actually serving `home.html`'s 2.48MB of bytes, title and all. Add new pages to that workflow's `cp` list in the same commit that adds the file — and since editing the workflow file itself isn't under its own `paths: src/viewme/public/**` trigger, a fix to the list needs `gh workflow run "Deploy product.interviewme.global → Azure SWA"` to actually redeploy, not just a push.
- **Confidential pages are password-locked and do NOT live in `src/viewme/public/` (2026-10-22).** The pitch deck, architecture, feed spec, pricing model, patent list and investor figures (`pitch-deck`, `architecture`, `feed-spec`, `pricing-question`, `patent`, `fp`) are HTML files in `src/backend/Explain.Api/PrivatePages/`, served only by `Features/PrivatePages` to someone holding an unlock token. On the website each of those addresses is a route in `src/viewme/public/staticwebapp.config.json` that rewrites to the small unlock page `private.html`. Passwords live only in the App Service setting `PrivatePages__Passwords` on `explain-global-api` (`label=password` pairs, comma separated; each person has their own so one can be removed; with none set everything stays locked). **Never put a confidential page back under `src/viewme/public/`** (anyone with the link could read it, which is how a prospective partner came to hold the whole pitch deck on 2026-10-21), and never put a password in the repository. To lock another page: add its HTML to `PrivatePages/`, add a route for it in the config, and do not add it to `deploy-product-interviewme.yml`. Images a locked page needs must be embedded in the page (data URIs), since the website's files are public.
- **Free months and the two recruiter tiers (2026-10-22).** Every new account is free for `FreePeriodMonths` (3) from sign-up with `FreePeriodMonthlyCap` (3) interviews a month (`Features/Entitlements`, settings row in SQL, edited on the admin Access page); recruiters get the same months and `RecruiterPrepCap` (10) prep links a month. **The paywall limits only bite once Enforcement is switched on, and on 2026-10-22 it was still OFF** (everything free and uncapped; read from `EntitlementSettings`), EXCEPT the self-service recruiter limits, which always apply. A recruiter signs up alone as role `recruiter-lite` (id 6: no `CAN_VIEW_CANDIDATE_PROFILE`, so no candidate data, client gifts, introductions or talent alerts); an admin approves them on the Access page, which adds the full Recruiter role. Gifts, introductions and alerts test for `CAN_VIEW_CANDIDATE_PROFILE` inline. Not built yet: an email before the free months end, and recruiter seat billing. The candidate subscription is **£3.99 a month** from 2026-10-23 (new Stripe price `price_1UTZT6KEj5soxpmhMoYkjjLU`, set as `Stripe__SubscriptionPriceId`; the old £4.99 price has no subscribers and can be archived). Someone who subscribes while still inside their free months gets a Stripe trial that ends on their free-until date (`CandidateSubscriptionService.TrialEndFor`), so the first payment is when the free months end. `CandidateSubscriptionService.PriceGbp` and the wording in `EntitlementRules.cs`, `SubscriptionPage.tsx`, the paywall and `home-v2.html` all say £3.99.
- **Two separate CORS policies, both need updating on any domain change:** the `.NET` backend's own CORS allowlist (`Program.cs`, `knownOrigins`) only covers calls made *to* the backend. The `p1coreb258` **Azure Blob Storage account has its own, completely independent CORS config** (`az storage cors list --account-name p1coreb258 --services b`) covering direct browser fetches to blob URLs — e.g. the TTS audio cache (`tts-cache` container) that `InterviewRoomPage`/LiveAvatar fetch straight from blob storage, bypassing the API entirely. Adding a new candidate-facing domain to `Program.cs` does **not** cover this — forgetting the blob storage side silently breaks cached TTS playback (falls back through LiveAvatar → plain TTS → the browser's native robotic `speechSynthesis`, and starves LiveAvatar of audio, so avatar mouths stop moving too) with no server-side error, only a browser-console CORS error against `*.blob.core.windows.net`. This exact bug broke voice + avatar lip-sync for a day during the 2026-09-08 TheInterviewChair.com rebrand, fixed 2026-09-09. Update both allowlists together on any future domain change.

## 4. Workflow rules

- **Verify before claiming done.** For backend changes: `dotnet build`. For frontend changes: `npx tsc -b --noEmit`. For anything UI-visible: run the local dev server and actually look at it in a browser before saying it's fixed — don't rely on types passing alone.
- **Commit, then push, immediately.** Never leave a commit sitting unpushed — CI/CD (GitHub Actions → Azure) is how everything actually goes live, so an unpushed commit isn't a fix yet.
- **When porting a module between portals, copy every file it depends on** — pages, components, utils, api files, assets — recursively. No partial copies, no "this one's probably the same." Run the type-check clean before committing.
- Don't ask for confirmation on routine tool calls (Bash, Read, Write, Edit, Grep, git commit/push) — proceed. Do still flag genuinely destructive or irreversible actions (force-push, `git reset --hard`, deleting a `.git` directory, dropping data) before doing them.
