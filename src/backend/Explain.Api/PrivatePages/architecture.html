How TheInterviewChair.com is built

Is it running on a box at home? No.

Everything runs on Microsoft Azure. Five web front ends sit on Azure Static Web Apps, one .NET 10 backend sits on Azure App Service, data sits in Azure SQL, Cosmos DB and Blob Storage, and every change goes live through automated GitHub Actions pipelines.

Built today: sending, editing and resending a prep, the invite email, the candidate's "received" list, and a recruiter preview of the interview. Also built: the recruiter's view of whether the candidate opened the prep, how many times they practised and how many questions they answered. By design the recruiter never sees answers or scores, and the candidate is told exactly that before they start.

Backend design

A vertical-slice backend: each feature owns its endpoint, request handler, validation and data access in one folder, so a feature can be understood, changed or removed without touching the rest.

Patterns in use

  • Vertical slices: one folder per feature under Features/
  • CQRS-style handlers through MediatR
  • FluentValidation on every request
  • A Result<T> type that maps to HTTP status codes in one place
  • Permission policies, not role strings, guard each endpoint
  • Rate limiting on every public route

Domain-driven design, plainly

The domain layer is small and pragmatic: entities for users, profiles and search events, with business rules sitting in the feature handlers beside them. It follows DDD's language and boundaries, but it is not a textbook aggregate-and-repository build, and I would not describe it as one.

Security and privacy

Keys and calls

  • No third-party API key ever ships to a browser
  • Every AI, voice, face and transcription call passes through the backend
  • Short-lived tokens for live faces, minted server side

Access

  • JWT authentication with per-permission endpoint policies
  • Brute-force lockout on login
  • Explicit CORS allowlists on the API and on storage

People's data

  • Private by default: candidates choose if and when to be found
  • Private blob containers, signed links per request
  • Account deletion and consent-based email lists
  • The CV analyser does not keep the uploaded CV

Delivery and observability

Commit to live

Each portal and the API has its own GitHub Actions pipeline that builds and deploys to Azure on push. Type checks and .NET builds gate each change. There is no manual server step.

See what is happening

Application Insights records exceptions and requests. The admin portal has an Activity Log with a visitor funnel, sources by campaign tag, a "pages opened" table, likely-robot labelling and a Subjects view of what people practise on.

Cost visibility

Serverless data stores and a right-sized API plan mean spend tracks usage. Provider calls are metered per interview, so the cost of one practice session is a known number.

Rules the agents run under

  1. Agents use tools, they do not own systems. An agent can only do what an existing API endpoint allows, with that person's permissions.
  2. No agent holds a provider key. Reasoning goes through the Model Router on the backend, the same as every other AI call.
  3. Anything that leaves the building needs approval. Emails and messages to third parties are drafted, then approved by the person or by a rule they set.
  4. Every run is logged. Input, tools called, output, tokens and cost, so any action can be explained afterwards.
  5. Every agent has a budget and a kill switch. Daily token and cost caps per agent, and one switch to pause a person's agent or all agents.
  6. Depth follows the plan. What an agent does for a candidate can map to subscription tiers, so Standard and Premium are different amounts of agent help.
